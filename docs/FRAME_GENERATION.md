# Frame generation integration

## 0.4.16 FSR multi-frame generation

Select FSR FG, enable **FSR multi-frame generation (DLSS Enabler)**, then choose 3X or 4X. Disabling the checkbox restores classic FSR 2X. The new backend supports SDR and HDR10/PQ; use classic FSR for scRGB. Latency reduction remains independently selectable. The supplied Enabler runtime is loaded privately and does not replace the game's native DLSS library.

GPU readbacks verify distinct, correctly ordered intermediate images at 3X and 4X. Hidden hardware checks cover live provider changes, resize, NR and HDR; these do not certify in-game pacing or image quality. The user's confirmed 0.4.15 XeFG timing fixes remain intact. PreSR and REST HUD isolation remain pending; see REPAIR_STATUS.md.

The 0.4.9 development path presents FFXIV's existing native D3D11 DLSS result through a private D3D12 frame-generation provider. It does not run an extra world DLSS pass. The native depth, motion vectors, camera matrices and jitter accompany the same real frame as its HUDless scene image. An unavailable provider retains ordinary presentation.

Version 0.4.9 creates the private presentation owner even when HDR, FG and independent latency start disabled. Live output changes recreate only its presentation output, preserving the game/ReShade buffer identity. Failed requests retain the committed format and matching transfer function. Native DRS is now an explicit quality choice independent of model control, rather than requiring all DLSS controls to be disabled.

For RTX 20/30, `prepare-sm86-runtime.ps1` stages the supplied SilyNoMeta v0.3.5-5 compatibility module. The bootstrap matches the real rendering adapter's DXGI LUID to CUDA, verifies the module's exact size and SHA256, requests FollowGame and host-owned UI handling, then initializes it before Streamline. The session retains the module for hook lifetime. Compatibility failures remain visible in the overlay and do not suppress independent Reflex initialization. Actual interpolation, 6X and dynamic MFG on SM75/SM86 still require target-hardware testing. The Ada-specific unlock and FG model preset overrides have not been ported.

## Providers and output formats

| Provider | Requested output limit | Latency integration | SDR | 10-bit BT.2020/PQ | 16-bit linear scRGB |
| --- | --- | --- | --- | --- | --- |
| NVIDIA DLSS-G | Up to 6X, capped by the active runtime/GPU | NVIDIA Reflex | Yes | Yes | No |
| Intel XeFG | Up to 4X with the optional verified unlock; otherwise runtime limit | Intel XeLL | Yes | Yes | No |
| AMD FSR FG | 2X | AMD Anti-Lag 2 when supported by the GPU and driver | Yes | Yes | Yes |
| FSR via DLSS Enabler | 2X/3X/4X | Independently selected controller | Yes | Yes | No |

Multipliers include the original frame: 6X means five generated frames per real frame. A successful options call is not proof of frame generation. The overlay reports actual provider presentation counts and may show 1X during warmup or when interpolation is skipped. The presentation owner is installed even from cold SDR/FG-off startup. Provider, enable/disable, multiplier, dynamic target and output-format requests can change live. SDK startup on a provider handoff can still take several seconds; it is not performed for multiplier or target edits.

Live provider changes stop the former provider, retire its GPU work, quiesce latency callbacks and recreate the provider's D3D12 presentation chain while retaining the ReShade D3D11 carrier. Latency reduction follows the selected provider: Reflex for DLSS-G, XeLL for XeFG, and Anti-Lag 2 when available for FSR FG. XeLL/FG markers require completed Sleep for the same frame id.

The "Keep latency reduction enabled with FG off" checkbox is enabled by default. Turning FG off releases interpolation resources and uses ordinary presentation while retaining the selected latency controller. Clearing this separate checkbox also disables latency reduction during ordinary presentation. Selecting the Off provider uses Reflex when the checkbox is enabled. FG retains the latency integration required by its provider. The setting keeps its existing `reflex` configuration key for compatibility.

Addon quality/model control is independent of FG, latency, NR and automatic depth. Native FFXIV DLSS evaluations supply their measured active subrects and jitter when controls are off; camera capture must still run without replacing native jitter. Native-DLSS frontend rendering is also retained for these independent consumers, without changing the game's selected upscaler or quality. This requires the game's DLSS pipeline; it does not invent approximate guides when no native evaluation exists.

Variable render resolution and dynamic MFG have separate contracts. In vanilla DRS mode, two private FG guide sets retain output-sized capacity and SDK tags describe only the current active region. Changes within that capacity do not reallocate buffers or reset FG history by themselves. DLSS-G's DRS flag is enabled with an explicit processing target latched from a valid native extent until the feature, output or mode changes; fixed addon presets clear it. Jittered motion-vector correction converts the preceding frame's jitter to current render-pixel units. Automatic depth keeps a stable output-sized R32 texture in native DRS mode, while fixed presets retain the prior compact texture. The extra DRS capacity is bounded and adds no color buffer.

Version 0.4.9 replaces the previous retained-session design. A handoff first detaches new latency calls, disables the old controller, retires GPU work and waits for outstanding latency calls. It then releases command lists, images, views, swapchain, SDK context/session, queue, fences and private D3D12 device before constructing the new owner. Streamline receives `slShutdown`; XeFG/XeLL contexts are destroyed before exact-byte restoration of the pacing/capability patches; FSR model/swapchain contexts and Anti-Lag are released. A retirement failure blocks unsafe replacement and is recorded explicitly. The native D3D11 device and ReShade carrier survive, as does NR's separate owner.

Temporary missing/coalesced inputs use DLSS-G's resource-retaining Off flag and the preceding valid dimensions. Explicit user disable/provider handoffs release allocations. The external SM75/SM86 compatibility module is an exception to module unloading: it installs opaque hooks without an unload API and remains process-resident. Full removal of those third-party hooks is not implemented or validated.

Always-on asynchronous recordings retain vendor messages and per-frame timing across provider changes; see [FG_DIAGNOSTICS.md](FG_DIAGNOSTICS.md). Historical validation notes below describe earlier builds and do not certify the current repair.

FSR FG is cross-vendor; Anti-Lag 2 is not. On an NVIDIA test system, the AMD driver latency API is unavailable and the interface reports that fact. No NVIDIA hardware latency result validates Anti-Lag 2 on Radeon. The official Anti-Lag 2 SDK supports RDNA 1/Radeon RX 5000 or newer with appropriate AMD drivers. See [AMD's integration and hardware requirements](https://github.com/GPUOpen-LibrariesAndSDKs/AntiLag2-SDK#support).

XeFG 5X/6X are not exposed in this milestone. XeFG interpolation is disabled in exclusive fullscreen; use a windowed/borderless presentation for it. DLSS-G capability remains subject to NVIDIA's GPU, driver and OS requirements; an installed DLL alone does not supply unsupported hardware capabilities.

## Frame timing, HDR and ReShade

Simulation markers attach to FFXIV's validated Framework virtual Tick boundary. The adapter resolves the actual Framework instance, leases its live virtual slot and chains any existing callable rather than assuming the canonical table is active. Camera data comes from the native world camera associated with queued render work. Explicitly infinite projections do not depend on unused far-plane storage. Invalid matrices/lens values still reject the camera. Bounded logs include rejection reasons and full matrices, and summaries count simulation calls, camera samples, accepted cameras and native captures. Guide allocation/copy is skipped until the native camera/frame boundary is valid.

FG waits for validated native camera/guides rather than constructing approximate motion or depth. Native guide regions are cropped to their active sizes, and the implementation checks texture bounds. From 0.4.4, capable DLSS-G runtimes use native `eDynamic` with the requested output target; the manual sustained fallback remains for unsupported DLSS-G and XeFG. XeFG's pacing hint prefers fresh provider-wait-adjusted CPU timing as in the working fork; this is not a measured GPU render time and is not used to retune the manual multiplier policy. Version 0.4.7 also follows the fork's multiplier transition: configure before the first enable; for a running context, disable interpolation, apply the new factor, present one ordinary frame, then re-enable. Stable frames do not repeat multiplier configuration. Complete native SR/NR and FG operations on the shared D3D11 immediate context use one transaction guard so native render and Present threads cannot interleave private context state changes.

Streamline tokens are borrowed SDK objects from a bounded pool. The [programming guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuide.md) requires non-concurrent token issuance and recommends carrying the simulation-start token to asynchronous rendering. Version 0.4.4 issues exactly once per native simulation ID, serializes that issuance, and reuses the matching token for all markers/constants/tags. Missing, expired or recycled tokens give ordinary warmup output rather than inventing an identity. The [DLSS-G guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md) documents native dynamic MFG capability and target control. No new Reflex frame limiter is inferred from the dynamic multiplier target.

All camera producer positions, including invalid entries, are consumed once by native world evaluation before other input rejection checks. Native failures explicitly discard their camera cohort. Missing cameras cannot reuse an older camera with a newer simulation ID. Accepted source/native IDs must advance; discontinuities, overwritten captures, focus/source/size changes reset history. Once world captures have started, ordinary unmatched Presents cannot keep advancing ahead of a render worker and permanently prevent it from catching up. Focus/provider invalidation keeps FIFO tombstones so future samples do not shift. Overflow beyond the bounded camera capacity fails closed until the evaluator catches up, rather than pairing wrong camera data; it is counted in the log.

The 0.4.2 game log recorded 9,786 camera samples, zero valid cameras, and successful Framework simulation callbacks. Every sample was rejected as an invalid affine view. Installed executable inspection shows the view operator at RVA 0x33CB60 consumes only XYZ from each padded row and supplies the homogeneous column implicitly. The producer at 0x261160 copies all 64 bytes, including padding. Version 0.4.3 explicitly expands the view to a true 4x4 matrix with fourth column (0,0,0,1), validates the finite orthonormal XYZ basis, and forwards the unchanged row-major right-handed reversed-infinite projection. All 30 full matrices captured in the log satisfy the meaningful basis checks. Tests retain actual logged XYZ/translation and reject malformed active values while ignoring even nonfinite padding. These RVAs are evidence for the installed binary, not hook fallbacks or promises about future game builds.

The same run recorded 538 skipped NR frames with repeated command-slot Busy fallback. Version 0.4.3 waits a bounded interval for an already-ended consumer when slots are exhausted, retaining the existing image/allocator count and processing current color rather than alternating full NR with clean DLSS. It does not wait for a future Present or reuse an old composited frame. Timeout latches a stable clean fallback with an error. The new `fg_probe --nr` mode warms the production two-pass model separately, then tests 120 steady frames per provider/checkbox phase with no artificial sleeps or intermediate readbacks, requiring every frame to apply NR without new skips, failures or model recreation. Its final readback checks changed finite RGB and unchanged alpha; a disabled NR control must remain clean.

The game and ReShade retain a D3D11 SDR compatibility surface. ReShade effects finish before the final SDR/PQ/scRGB result reaches the presenting provider. The private D3D12 device is created through the independent device factory, avoiding unrelated ReShade D3D12 lifetime callbacks and the legacy REST global-state problem encountered during NR integration. HDR scene reconstruction and UI composition continue through the existing HDR path.

Version 0.4.1 also excludes addon-owned Streamline helper DLLs under the private runtime subtree from native FFXIV DLSS discovery. They had been mistaken for a second native SR runtime, which blocked the real native Evaluate hook and left NR at zero applications and FG at 1X. The exclusion is limited to addon-owned runtimes; tests still reject genuine duplicate game SR modules. The in-game test must first confirm increasing native DLSS and NR evaluation counters before judging FG.

Version 0.4.5 uses two bounded input sets, each containing HUDless color and depth/motion guides. Their late completion fences cover the provider's actual input lifetime. The final-color scratch image is still single; a separate early fence protects its copy into the SDK backbuffer before D3D11 may overwrite it. Three command slots retain late allocator retirement. Only immediate-context work holds the D3D11 transaction guard. SDK Present and its input-retirement query/wait run without that guard or the capture-engine mutex, allowing the native worker to fill the other set during pacing. Output transitions hold a separate recursive presentation lease acquired before D3D11 ownership, including fullscreen and resize. Frame/cohort and HDR metadata are sealed before unlocking, so returning from an older Present cannot erase the newer capture.

An SDK input-retirement failure quarantines the bounded generation and stops further input writes. A game-queue fence alone cannot prove completion on the SDK's private queues. Ordinary final-color presentation can continue, but provider transitions cannot free the uncertain owners and FG requires restart to retry. This error path deliberately retains resources until process exit. Quality changes retire only the pending input set's previous guides; they do not stop a provider currently presenting the other set. Provider changes/output resizes still retire all pending D3D11 writes and SDK work before allocation/lifetime changes.

The second input set adds `output_width * output_height * output_bytes_per_pixel + guide_width * guide_height * 8` bytes before allocation alignment. At 3840x2160 PQ with 2560x1440 guides this is about 59.8 MiB; scene/pre-effect/final scratch and NR model storage are not duplicated. ReShade depth effect metadata is cached per reload epoch, and same-device NR attachment avoids the model-host mutex on the per-Present path.

## Runtime provenance and preparation

`runtime/fg/manifest.json` records exact SHA-256 hashes, lengths, versions and notices. Files distributed on disk remain the unmodified official binaries:

| Component | Pinned source | File version |
| --- | --- | --- |
| Streamline/DLSS-G | [Streamline 2.14.16 SDK](https://github.com/NVIDIA-RTX/Streamline/releases/tag/v2.14.16), tracked in `runtime/manifest.json` | SL 2.14.16; DLSS-G 310.9.16.0 |
| `libxess_fg.dll` | [Intel XeSS SDK 3.0.2](https://github.com/intel/xess/releases/tag/v3.0.2) | 1.3.1.78 |
| `libxell.dll` | Same Intel SDK | 1.3.2.10 |
| `amd_fidelityfx_framegeneration_dx12.dll` | [FidelityFX SDK 2.3.0](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/tree/60f4ea81909200d8542eca14dccb2628b763a9a3), signed binary | 4.0.1.2740 |
| Anti-Lag 2 header integration | [Anti-Lag 2 SDK 2.0.0a](https://github.com/GPUOpen-LibrariesAndSDKs/AntiLag2-SDK/releases/tag/v2.0.0a) | Header integration; no extra runtime DLL |

The AMD DLL contains multiple implementations; this integration queries available versions and selects the classic 3.1 frame-generation implementation for the current cross-vendor route. The DLL's 4.0.1 file/API version does not mean that the ML-only implementation runs on every GPU.

Prepare the pinned Intel/AMD files with `tools/prepare-fg-runtime.ps1`. `-Offline` uses the verified archives/files already under `.cache`; it fails if a required input is missing or has a different hash. `-ValidateOnly` reads the manifest and all seven runtime/license files without writing. `-OutputDirectory` allows isolated package verification without changing the production runtime folder. NVIDIA runtime preparation remains in `tools/prepare-runtime.ps1`. Neither script installs into FFXIV.

The optional XeFG 4X unlock and generated-frame scheduler are adapted from the user's previously tested SirenBrink OptiScaler fork under GPL-3.0-or-later. Source attribution is retained in `include/xivrender/xefg_pacing.hpp`; the project GPL is in the root `LICENSE`. The unlock checks PE timestamp `69CB0F4D`, image size `015ED000`, executable section bounds and every expected instruction before editing the mapped 1.3.1.78 module. It does not alter the on-disk Intel DLL. Unknown provider builds retain their ordinary supported limit. This compatibility path is distinct from Intel's officially supported 4X MFG on Intel Arc hardware.

Ship `xess.LICENSE.txt`, `fsr.LICENSE.md`, `fsr.THIRD_PARTY_NOTICES.md` and `antilag2.LICENSE.txt` beside the FG DLLs, and retain the NVIDIA notices shipped with its separate runtime bundle.

## Validation status and limits

The 0.4.6 game test did not resolve the reported problems. The user confirmed smooth DLSS-G with dynamic MFG at 4X, but manual 6X restored regular stutters. XeFG 4X collapsed to roughly 6 real/24 presented FPS, and ordinary presentation remained around 24 FPS after FG and NR were disabled. The saved game logs are in `diagnostics/fg-047-20261028/`.

After NR was disabled, the log placed roughly 32 ms per frame inside the ordinary native DXGI Present call; the other measured addon CPU stages were below 0.5 ms. Local GPU memory was about 6.5 GB against a 15.97 GB budget, later falling below 3 GB at the frontend while the ceiling persisted. No SDK teardown failure or out-of-memory error was recorded. These observations do not establish a leak, GPU execution cost or a particular driver limiter. The 24 FPS ceiling matches 144/6 after the last manual DLSS-G factor, but that relationship is an investigation clue, not a proven cause.

Version 0.4.7 corrects the documented feature lifecycle, ports the XeFG factor transition and separates ordinary-frame latency control from FG. Fixed-ratio DLSS no longer sets DLSS-G's `eDynamicResolutionEnabled` flag: changing a quality preset does not mean the render resolution varies dynamically within that preset. This input-resolution flag is separate from native dynamic-MFG selection and does not change its policy. In-game resolution of the reported stutter and persistent slowdown remains unverified. New summary telemetry records forwarded Present intervals/flags and whether the existing early-copy fence was already complete before a slow Present, without adding a GPU wait or per-frame log writes.

Version 0.4.6 removes the addon's focus disable, camera FIFO clearing and focus-driven history resets. It continues valid requests/inputs in the background while preserving the provider's actual HWND and OS policy. NR pause remains independent; hidden/occluded DLSS-G may still return 1X. Controlled false-focus/regain checks require continued input/history, not invented generated counts.

The output wrapper now exposes the native D3D11 carrier's maximum-latency semantics and never exposes a private FG waitable handle. Explicit application waitable-chain requests bypass wrapping, and ResizeBuffers cannot add that creation flag. [NVIDIA's 2.14.16 integration guide](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.16/docs/ProgrammingGuideDLSS_G.md#121-frame-latency-waitable-objects) documents competing waiters as a pacing failure. The game log did not record these calls before this correction, so it is a demonstrated contract violation, not a proven explanation for the user's regular stalls. The new periodic counters identify actual application latency/statistics queries. The Output regression injects private pacing signals and verifies the logical application cannot read or mutate them, with positive sensor controls.

Version 0.4.6 changed Off to retire the vendor output/model and create an ordinary private output on the same retained D3D12 device. Re-enable recreates the provider output, not the process-wide SDK session. Ordinary output allocates only final-color scratch. The 0.4.7 latency checkbox correction keeps the selected latency controller available independently of this output replacement.

XeFG's enable and multiplier calls occur only when their values change; the pinned Intel header warns repeated multiplier configuration can cause compilation/reallocation. FSR's configure/PrepareV2 IDs now use a contiguous local sequence rather than possibly skipped/zero simulation IDs, matching [AMD's documented frame-ID requirement](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/blob/main/Kits/FidelityFX/framegeneration/include/ffx_framegeneration.h). Native camera/image validation remains separate. FSR native counts retain every asynchronous batch and UINT wrap; measured windows replace single-Present integer-ratio guesses. The overlay shows observed ratio plus real/presented FPS. These counts do not establish physical scanout cadence.
